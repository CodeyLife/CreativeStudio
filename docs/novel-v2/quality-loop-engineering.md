- 状态标记：✅ 已落地（本轮）/ 🔜 提议（待排期）

## 一、实证问题分类与根因

本轮审核共处置 20 条 issue（4 blocker/major 闭环、7 条过报封存、6 条 seam 登记、1 blocker+2 major 闭环于 ch15）、1 个管线障碍（重审入口封锁）。按根因分五类：

### A. 合同变更残留类（旧内容未随新合同移除）
- 实证：ch15 修养室修订恢复"拖走"后，旧版"如蒙大赦逃走"段落残留——同一场景两个互斥结局，且通过了三轮评审与作者批准（blocker）
- 根因：合同变更只登记了"新结局"的修订窗口；**被取代的旧结局段落位于窗口之外**，无人负责移除。逐行 diff 的"无删改"在合同变更场景下恰恰是失败信号，但批准环节没有机器强制核对口诀

### B. 实体/资产账本类（可数事实跨章漂移）
- 实证：灵石（ch1 怀里两块 → ch2 床角一块 → ch8 几块）、云纹草（ch13 交一株 → ch14 回述两株）、容器（星屑砂 包/瓶）、战利品（ch6 背骨/布袋未在 ch5 采集）
- 根因：fact-extraction 提取事实但不维护**可数实体的状态账本**（数量/位置/容器/持有人随章节的快照）；审校上下文没有资产对照输入，reviewer 靠记忆无法追踪

### C. 同类残留类（修一漏一）
- 实证：ch6 POV 修复移除了登记位置的违例，但同类"疯狗"体感句在窗口外存活，直到下一轮才被发现
- 根因：targeted 修订按窗口只改登记段落；**同类违例的全章扫描**不存在，改一类问题需要人工把所有位置逐一登记

### D. Issue 生命周期类（陈旧意见反向有害）
- 实证：ch2 期限条目要求在期限建立章之前回填引用——采纳将复现已修复的时序矛盾；ch6×5 条证据引用已删除文本
- 根因：issue 创建后**不随文本/合同变化失效**；消费方（targeted 载入）不做证据在场复检；意见建议引用的事实与建立章的关系无校验

### E. 管线可靠性类（依赖物被清理）
- 实证：10/15 章重审入口被"找不到历史 blueprint"堵死（:draft artifact 被保留策略清理）
- 已修复 ✅：回退 execution_blueprints 表行（工作流真正的加载源）+ 三用例回归测试——模式沉淀：**preflight/工作流依赖物不得指向保留策略可清理的产物，除非存在权威表行兜底**

### F. 表层一致性类（全书风格漂移）
- 实证：158 处半角直引号混布 4 章、全书唯一内嵌标题行
- 根因：无全书 style-sheet 门；生成的表层约定（引号体系、标题格式）无确定性校验

## 三、对策设计细节

### 1. Evidence 闭环校验（P0）——把本轮人因失误变成机器门

issue 的 `evidenceQuote` 是必填字段且已有创建时校验（`isEvidencePresentInText` / `markEvidenceUnverified`）。补齐另外两个时点，形成闭环：

- **消费时**（`loadTargetedReviewIssues`）：逐条复检 evidenceQuote 最长连续片段是否仍在当前正文。不在 → 标注 `evidence-stale` 并**不作为修订窗口**（或要求编辑者显式确认后降级 ignored），杜绝"按已删除的证据去改正文"与"过报引用复活旧矛盾"
- **解决时**（commit 前的结构报告 / 审批 payload）：对本次 targeted 的每个 issue 生成机器核对结论——evidenceQuote 是否已从候选正文消失（删除/改写类）、建议关键词是否在场（新增类）。失败项进批准门禁的醒目清单

覆盖：A（旧结局段落若在 evidence 引用范围内，删除类核对直接拦截 ch15 式残留）、D（消费时拦截陈旧 issue）。
边界：evidenceQuote 被作者改写但矛盾仍存在的情形无法机械判定——机器只核对"引用是否消失"，语义是否修对仍由评审与批准者判断。

### 2. 批准门禁机器核验清单（P0）

targeted 修订进入 `manual-review-required` 时，payload 附 `machineCheck`：

```json
{ "evidenceRemoved": true, "suggestionKeyPhrasesPresent": ["拖走，送去修养室"], "windowsChanged": [57], "windowsUnchanged": [], "remainingWindowIssues": [] }
```

批准者（人/编排 LLM）对着机器结论签字。本轮 ch15 批准失误（"逐行 diff 无删改"被当成合格信号）的直接对策：**机器先核对"该删的删了吗、该加的加了吗"，人只对机器无法判定语义的部分负责**。
边界：清单是核对辅助不是替换判断；语义质量（改得好不好）仍走评审。

### 3. 实体/资产状态账本 + 序列证据投影（P1）

复用 `openPromises` 已验证的模式（账本 → 按建立章投影 → draft/review/revision 对照指令）：

- fact-extraction 增提 **countable 实体状态**：主角/关键人物持有的可数物（灵石数量、灵草株数、材料清单）及其变化事件（获得/消耗/被夺/移交）
- 新表或复用 claims：`entity` + `state`（数量/位置/容器）+ `narrative_order`；读取层按章投影 `entitySpans` 进 `SerialContextSnapshot`（与 characterSpans/subjectSpans 同构）
- 渲染层对照指令："本章涉及实体 X 的数量/位置须与账本一致；账本缺失时提示登记"
- 写入层同伏笔教训：内容派生键 + ON CONFLICT 合并，避免重复登记膨胀

覆盖：B 全类（灵石、云纹草、容器、战利品）。边界：同义改写的实体对齐不做机械判定（与 narrative-elements 去重同一边界）；数值推断（"几块""十来个"）只登记模糊值。

### 4. 同类残留启发式扫描（P1）

修订 commit 后，按本次 issue 的 rule 类对**全章**跑一次启发式扫描，命中进结构报告 hints（不阻断）：

- POV 类：非视角人物名 + 内心动词（不悦/暗惊/心中/暗想/感觉）同句 → 候选清单（词表仅限功能词，不嵌题材样本）
- 标点类：引号奇偶配对、半角残留、行首悬挂闭引号
- 数量类：数字+量词邻近账本实体 → 与账本状态对照

覆盖：C（修一漏一在 commit 点就被列出，而不是等下一轮人工审核）。边界：启发式误报进 hints 供人复核，不设硬门——与 cinematicHints 同哲学。

### 5. Style-sheet 确定性门（P1）

commit 结构报告（inspectManuscript）新增确定性表层检查：引号体系全书统计（半角/全角占比）、内嵌标题行、段落格式异常。提示级输出 + 维护建议（指向对策 8 的批量通道）。**刻意不做**错字词表（泛化红线：堆叠 case-specific 模式列表违反 AGENTS.md）。

### 6. 时序反向校验（P2）

意见建议若引用承诺/期限/已知事实，按账本 `establishedAtOrder` 对照目标章 narrative order：**建立章晚于目标章 → 自动标注"采纳此意见将制造时序矛盾"**（ch2 期限条目即此类的实证）。依赖对策 3 的账本扩展（openPromises 已提供承诺类的现成数据）。

### 7. 段落号自动定位（P2，✅ 已落地 2026-09-08）

issue 创建 API 用 evidenceQuote 在正文反推段落号（非空行序），与调用方传入值不一致时在响应中返回两者并提示校正。本轮编辑器行号（71）与系统段落号（实际窗口错位）导致的修订放置错误在源头消除。

### 8. 批量规范化维护通道（P2，✅ 已落地 2026-09-08）

把本轮手搓的"确定性文本变换脚本 + proposedText 作者提案 + 串行 full review"固化为维护脚本：输入变换类型（引号规范化/标题行清理/…）+ 章节清单，逐章生成 proposed text 并串行提交。沉淀两轮实证的操作要点：同项目审校必须串行（并行撞基线）、targeted 窗口不适合全章性变换。

### 9. 工作流依赖物权威兜底原则（P0，已落地 ✅）

原则：preflight/工作流消费的依赖物，若同时存在于"可清理产物"与"权威表行"两处，查询必须提供表行兜底。已落地：`findHistoricalBlueprintForDocument` 回退 execution_blueprints 行（回归测试三用例）。后续新增工作流入口按此原则自查。

### 10. 逐章顺序阅读纳入弧收口流程（P1，流程项）

两轮审核实证互补：issue 驱动审核看单章快照，**逐章顺序阅读才能暴露资产账本断链与场景互斥**。约定：每弧收口（最后一批章节 commit 后）执行一次 1→N 顺序沉浸阅读，产出读者视角报告；可与弧 3 规划前的事实梳理（伏笔账本合并）同批执行。

## 四、刻意不覆盖的边界

1. **语义等价判定**：改写后的句子与证据语义是否一致、实体同义改写是否同一物——不做机械判定，交评审与账本模糊值
2. **风格取舍**：技术隐喻密度、节奏疲劳等 craft 类意见保持 reviewer+作者决策，机器只提供线索（避免个案偏好固化为硬门）
3. **硬门范围**：新增机制全部为 hints/清单/标注，唯一的硬门仍是既有 commit gate（三审 + 分数守卫 + 无 blocker）；不新增阻断级自动拒绝
4. **泛化红线**：所有启发式词表仅限功能词（内心动词、量词、标点码位），禁止嵌入角色名、题材样本、特定短语
