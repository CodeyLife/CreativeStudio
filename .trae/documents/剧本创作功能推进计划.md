## 二、阶段一（P1，本次实现）

### 2.1 后端：创意短剧管线扩展

**文件：[short-script-h3.ts](file:///i:/Projects/CreativeStudio/src/novel-v2/application/short-script-h3.ts)**

1. **时长上限扩展（覆盖"几分钟"）**：
   - `MAX_SHORT_SCRIPT_TARGET_SECONDS`：60 → **180**（3 分钟）
   - `MAX_SHORT_SCRIPT_SEGMENTS`：8 → **36**（180s ÷ 最短单段 5s = 36，cap 与上限自洽）
   - `generateShortScriptH3` 中 `maxTokens: 16_000` 与 `compileStageContext` 的 `reservedOutputTokens: 16_000` → **32_000**（36 段 × 每段约 500 token 的六段结构 promptText，16k 会截断长时长产物；注释说明推导依据）

   - `ShortScriptRecord` / REST 响应无接口变化（`targetDurationSeconds` 字段已有）；幂等键含 targetDurationSeconds + 契约版本，老产物复用不受影响
2. **structuredData 落库创意来源**：`persistShortScriptArtifact` 的 `structuredData` 增加 `idea`（全量）与 `instruction` 字段——历史列表语义展示的依据（对齐用户偏好：语义化渲染、不露原始 JSON/UUID）

### 2.4 真实生成验证脚本

**新文件：`scripts/novel-v2-script-validate.ts`**（初始化模式对齐 novel-v2-api.ts：loadRuntimeEnv → resolveNovelRuntimeConfig → repository/skillProvider/model gateway）

用法：`npx tsx scripts/novel-v2-script-validate.ts --project <projectId> [--document <docId>] [--idea <创意文本>] [--duration 30] [--json <输出路径>]`

流程与指标（每项写入报告）：
1. **章节剧本路径**（`--document` 提供时）：调 `generateChapterScriptH3` 真实生成
2. **创意短剧路径**：调 `generateShortScriptH3` 真实生成（`--idea` 缺省时用一条内置的跨题材通用创意常量，不绑定特定作品）
3. **指标采集**：
   - repair 触发率：查 `model_invocations`（`workflow_run_id LIKE 'short-script:%'` 或章节剧本对应 taskId 前缀）统计 invocation 数、candidate_index、`error_category='schema-validation'` 次数、token 用量、耗时
   - cinematicHints 密度：`hints 数 / 片段数`
   - 结构校验：一次通过 / 经 repair 通过 / 最终失败
   - 时长窗口命中：总时长 vs 目标偏差
4. **剧作层 LLM 评审**（对齐用户偏好：LLM 评审优于正则）：用 model gateway 发起一次评审调用，评审维度取自 short-drama-writing 方法论的题材无关项（开场钩子形态、情绪节点节奏、出口钩子、伏笔-反转配对），输出单行 `PASSED` 或可执行 issue 列表（与规划级审核的文本意见契约一致，复用 `src/novel-v2/text-review.ts` 的解析思路）；评审结论与证据一并入报告
5. 输出：stdout 人类可读报告 + `--json` 时落结构化 JSON（供后续 P2 学习闭环作为证据源）

## 四、阶段三（P3，方向性规划）

1. **共享定义预设接入创意模式**：`generateShortScriptH3` 读取项目级 subject preset（替换 hardcoded `shared: { lines: [], maxLabel: 0 }`），幂等键纳入预设哈希；ScriptStudioPanel 复用 `SharedSubjectsEditor`

3. **超 3 分钟短剧**：单次结构化生成在 36 段/token 预算处封顶；更长剧情需分幕生成再拼装，作为独立契约演进项
4. **双契约演进纪律**：chapter 契约与 short 契约独立演进但共享校验管线，任何一侧升级须双向回归（现有测试已覆盖，保持该纪律）

## 五、假设与决策

| 决策 | 依据 |
|---|---|
| 时长上限取 180s 而非更高 | 36 段 × ~500 token/段 ≈ 18k 输出 token，32k 预算内可控；>3 分钟需分幕架构（P3） |
| 历史列表走独立 `/list` 端点，不改既有 GET 语义 | 既有 GET 语义（最新一条）已被前端封装依赖 |
| structuredData 存全量 idea | 用户输入文本体量小，全量存储便于幂等审计与列表语义展示 |
| 剧作层评审用 LLM 而非正则 | 用户偏好（memory）+ AGENTS.md 泛化优先原则 |
| 前端不新建测试基建 | 项目前端现存零测试文件，遵循现状以 tsc/lint 验证 |
| 验证脚本内置的默认创意为跨题材通用常量 | AGENTS.md：禁止 case-specific 样本固化 |
